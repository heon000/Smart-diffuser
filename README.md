# 날씨 기반 AI 조향 및 개인화 스마트 디퓨저 (Weather AI Smart Diffuser)

주변 환경 정보와 사용자 입력을 바탕으로 향기와 기기 동작을 제어하는 **IoT 기반 스마트 디퓨저 프로젝트**입니다.  
ESP32와 FreeRTOS를 기반으로 센서 측정, 음성 처리, 네트워크 통신, 디스플레이 UI를 함께 다루며, AWS Lambda 백엔드와 연동하는 구조로 개발하고 있습니다.

> 이 저장소는 현재 팀 프로젝트로 진행 중인 스마트 디퓨저 시스템을 바탕으로,  
> **포트폴리오 및 코드 정리 목적**으로 import하여 관리하는 공개용 저장소입니다.  
> 원본 협업 저장소는 팀장이 관리하는 비공개 레포지토리이며,  
> 본 저장소는 기능 구조와 구현 흐름을 정리하기 위한 사본 성격의 저장소입니다.

## 1. 프로젝트 개요

- **진행 기간**: 2025년 종합설계 프로젝트 시작 / 현재 기능 확장 및 고도화 진행 중
- **프로젝트 형태**: 6인 팀 프로젝트
- **개발 배경 및 목적**
  - 단순한 디퓨저를 넘어, 주변 환경과 사용자 입력에 반응하는 스마트 디퓨저 시스템을 구현하고자 시작했습니다.
  - 초기에는 개인 사용 환경을 중심으로, 음성 입력과 날씨 정보를 반영하는 디퓨저를 구상했습니다.
  - 이후 프로젝트를 발전시키는 과정에서, 개인용 기기를 넘어 **호텔 로비, 카페 등 공간 단위 환경에 적용 가능한 B2B 관점의 스마트 디퓨저**로 방향을 확장했습니다.
  - 이에 따라 임베디드 환경에서 센서 처리, 네트워크 통신, UI 제어를 통합하고, 공간의 소음 환경과 운영 편의성을 함께 고려하는 형태로 디벨롭하고 있습니다.

## 2. 기술 스택

- **개발 언어**: C++ (Arduino Framework)
- **하드웨어 플랫폼**: ESP32
- **태스크 관리**: FreeRTOS
- **하드웨어 인터페이스**: I2S, UART, GPIO, ISR(인터럽트)
- **네트워크 / 백엔드**: Wi-Fi, HTTP/HTTPS, AWS Lambda
- **디스플레이 / UI**: Nextion HMI
- **주요 라이브러리**
  - `ArduinoJson`
  - `WiFiManager`
  - `HX711`
  - `DFRobotDFPlayerMini`
  - `Adafruit_NeoPixel`

## 3. 실행 방법

### 1) 실행 전 준비

- ESP32 개발 보드와 Arduino IDE 또는 ESP32 업로드가 가능한 개발 환경이 필요합니다.
- Wi-Fi 연결 환경이 필요합니다.
- AWS Lambda 또는 연동 대상 서버 주소 및 필요한 설정값을 사전에 준비합니다.
- Nextion 디스플레이, 마이크, 로드셀 등 사용 중인 하드웨어 구성이 필요합니다.

### 2) 기본 실행 흐름

1. 프로젝트 소스코드를 내려받아 ESP32 개발 환경에서 엽니다.
2. 보드 및 포트 설정을 완료합니다.
3. Wi-Fi 및 서버 연동 설정값을 점검합니다.
4. 펌웨어를 업로드한 뒤 기기를 실행합니다.
5. 초기 설정 후 디스플레이 메뉴를 통해 원하는 모드를 선택합니다.

### 3) 주요 사용 흐름

- **초기 네트워크 설정**: AP 모드 접속 후 Wi-Fi 연결
- **설정 모드**: 로드셀 영점(Tare) 조정 및 장치 상태 점검
- **Ambient Mode**: 주변 소음 데이터를 기반으로 서버 연동
- **Voice Command**: 음성 녹음 후 서버 분석 결과에 따라 기기 제어
- **Weather Sync**: 날씨 정보 기반 향 분사
- **OTA Update**: 무선 펌웨어 업데이트 수행

### 핵심 포인트

- **환경 감응형 제어**
  - 마이크를 통한 소음 측정, 날씨 데이터 수신 등을 바탕으로 기기 동작을 제어
  - 단순 수동 제어가 아니라 외부 상태를 반영하는 구조로 설계
 
- **공간형 사용 시나리오로의 확장**
  - 개인 사용자 중심 흐름에서 더 나아가, 호텔 로비나 카페처럼 공간 단위 환경에 적용 가능한 방향으로 확장
  - 주변 소음 환경을 반영하는 Ambient Mode를 중심으로 활용 범위를 넓힘

- **FreeRTOS 기반 태스크 분리**
  - 센서 처리, 네트워크 요청, UI 갱신을 분리해 동시에 동작할 수 있도록 구성
  - 블로킹을 줄이고 응답성을 유지하는 방향으로 설계

- **비동기 하드웨어 제어**
  - 로드셀 등 센서 데이터 처리 시 인터럽트 기반 흐름을 활용해 병목을 줄이는 구조 적용
  - 메인 루프를 오래 점유하지 않도록 설계

- **서버 연동 기반 확장 구조**
  - 음성 명령, 날씨 정보, 추천 로직을 기기 내부에 모두 고정하지 않고 서버와 연동
  - 펌웨어와 백엔드 기능을 분리해 확장 가능성을 확보

- **디스플레이 및 앱 중심 사용자 인터페이스**
  - Nextion HMI와 어플을 통해 현재 모드, 잔량, 상태 정보를 확인할 수 있도록 구성
  - 임베디드 기기에서도 사용 흐름이 보이도록 UI를 설계

### 주요 구성 요소

- **ESP32 펌웨어**
  - 센서 입력 처리
  - 모드 전환
  - 네트워크 요청 및 응답 처리
  - 모터, LED, 오디오, 디스플레이 제어 담당

- **AWS Lambda / 서버**
  - 환경 데이터 및 음성 입력 분석
  - 기기 제어에 필요한 응답 반환

- **Nextion UI**
  - 상태 표시
  - 모드 선택
  - 진행 상황 시각화 담당

## 7. 개발 과정에서 고려한 점

### 1) 프로젝트 활용 범위 확장
초기에는 개인 사용 환경을 중심으로 음성 입력과 날씨 연동 기능을 강조한 디퓨저를 구상했습니다.  
이후 프로젝트를 발전시키는 과정에서, 공간 환경에 적용 가능한 형태로 활용 범위를 넓히기 위해 Ambient Mode와 운영 편의성을 함께 고려하게 되었습니다.

### 2) 임베디드 환경에서의 동시성 처리
센서 측정, 네트워크 요청, UI 갱신, 장치 제어가 한 번에 얽히기 때문에  
단일 루프에서 모두 처리하면 응답 지연이 커질 수 있다고 판단했습니다.  
그래서 FreeRTOS 태스크 분리를 통해 기능을 나누는 방향으로 구조를 설계했습니다.

### 3) 하드웨어 제어와 서버 연동의 분리
추천 로직이나 외부 정보 처리를 모두 기기 내부에 넣기보다,  
서버와 연동해 필요한 결과를 받아오는 구조가 유지보수와 확장에 더 적합하다고 보았습니다.  
이에 따라 펌웨어는 제어와 상태 관리에 집중하고, 분석 로직은 서버 쪽으로 분리하는 구조를 택했습니다.

### 4) 사용자에게 보이는 상태 정보의 중요성
임베디드 장치는 내부 동작이 보이지 않으면 사용자가 현재 상태를 이해하기 어렵습니다.  
그래서 디스플레이를 통해 모드, 진행 상황, 잔량 같은 정보를 보여주는 UI 흐름을 함께 고려했습니다.
